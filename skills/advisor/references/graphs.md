# Optional graphs and evidence references

Use a graph when independent ownership or real data dependencies make the work
clearer. Direct work and a single maker never require a graph. A graph is a plan
and visibility aid, not a permit to launch, repair or finish an agent.

## Choose useful boundaries

Every node should earn its place through parallelism, specialization, an independent
judgment or a substantial deliverable. A dependency means the downstream task
actually needs upstream output; do not add edges for conventional role order.
The advisor plans, investigates, and synthesizes findings directly. Builders and
checkers own investigation, local planning, implementation or repair, and verification
within their assigned scope. Each author verifies plausibly affected browser journeys;
do not turn that responsibility into a separate graph stage. Required agentic PR
review stays in the project's review workflow; a graph does not add a local gate.

`advisor_graph_plan` records the plan and checks structural consistency. Positive
parallelism and a valid DAG describe a schedule; there is no runtime node or repair
quota. Writer coordination belongs to the advisor. Keep one writer per checkout,
including yourself, and give parallel writers distinct registered Git worktrees.
Honor explicit user spend/concurrency limits without inventing additional ceilings.

Revise a plan when new evidence changes the useful work. Retain previous ownership
and evidence references; never rewrite what a worker actually read or did. A stale
plan or unavailable evidence should be visible, not prevent unrelated authorized
work. Structural mistakes in an optional plan are not a reason to block graphless
execution.

## Execute and inspect

1. Launch genuinely independent tasks together; use ordinary completion notifications.
2. Start dependent work when the inputs it actually needs are available. Investigation
   or repair can consume a failed implementation without pretending it passed.
3. Use the handoff summary when sufficient. Search the run's recorded transcript and
   inspect source, commands, tool results or other artifacts when detail is useful.
   A terminal pane tail is not the full session history.
4. Preserve maker/checker independence wherever independent review is required.
   A role label or a PASS summary never establishes verification by itself.
5. Continue an authorized repair while there is a useful next strategy or new
   information. Reassess unproductive repetition; do not stop because a graph
   counter ran out. Explicit user limits remain binding.

## Preserve evidence without making it authority

`advisor_graph_evidence` associates an owned run/attempt with a plan node and returns
evidence references. Keep these references when useful for downstream work; the
caller can open the original capture or search the recorded session rather than
paste entire upstream reports into every launch.

A missing, changed or stale reference is a limitation to report, not a launch veto.
Do not claim a worker consumed a newer report than it actually received. Plan edits
and successor associations preserve prior run attribution and immutable captures.
Replacing a plan node does not stop its previous worker or release its write
surface: inspect execution state and coordinate ownership explicitly.

Refresh the relevant association after a material change. A historical PASS stays
historical. Trusted host checks establish only their actual invocation and tested
surface; stale/unknown proof never becomes verified because a graph says complete.
A graphless task uses its normal handoff, recorded transcript and artifacts.

The legacy `GRAPH:` block, when present, is correlation metadata, not an additional
report format, authority grant or required token to execute work.

## Child advisors

Delegate an outcome, not a graph recipe. A child uses the same advisor doctrine and
chooses direct implementation or useful helpers. Parent-outcome identity is supplied
by the runtime; sibling graphs retain their own namespace. Accounting records work
across descendants but imposes no lifetime launch/reply/task allowance.

A parent turn can settle while descendants remain active; that does not mean its
integrated outcome is finished. Report outstanding children, keep their workspace
owned, and wait for the actual evidence needed before delivery or teardown.
Cancellation is explicit and never inferred from a summary, silence or an old PASS.
Use supported identity-checked recovery, not blind replay or manual lock edits.
